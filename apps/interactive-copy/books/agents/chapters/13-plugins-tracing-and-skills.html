In this chapter, we will learn how agl keeps the loop and the graph small: everything that is not control flow is a plugin, an object with some of a dozen hook methods. We will read the built-ins, learn what to log and why the trace is the most important file in the project, meet the two plugins that make an unattended agent safe, and learn why a markdown page in skills/ is the cheapest way to change an agent's behaviour. By the end you will write a plugin in ten lines and know which of the built-ins every production loop should carry.

The analogy: the people around the reporter

The reporter writes the story. Around her, without touching it, are the people who make the newsroom work: the archivist who logs every call (Trace), the news editor who shouts progress across the room (Console), the managing editor who pulls the plug on a story that has eaten its budget (Budget), the sub-editor who trims old notes so the file stays readable (Compact), the lawyer who must sign off before anything risky goes out (Approval), and the style guide on every desk (Skills). None of them is in the loop. All of them see everything it does.

Hooks

A plugin is an object. The loop and the graph call named methods on it, if they exist.

class Plugins:
    def __init__(self, *plugins): self.items = list(plugins)
    def emit(self, hook, *args):
        for p in self.items:
            fn = getattr(p, hook, None)
            if fn: fn(*args)
    def system_prompt(self, run) -> str:            # plugins may append text to the system prompt
        return "\n\n".join(t for p in self.items if (fn := getattr(p, "system_prompt", None)) and (t := fn(run)))
loop    on_run_start(run)                 on_run_end(run, answer)
        on_llm_request(run, messages)     on_llm_response(run, reply)
        on_tool_call(run, name, args)     on_tool_result(run, name, args, result)
        on_evaluate(run, verdict)
graph   on_graph_start(graph, state)      on_graph_end(graph, state, path)
        on_node_start(graph, node, state) on_node_end(graph, node, out, error, ms)
        on_route(graph, router, label, target)
        on_event(graph, node, kind, ev)   a node called state["_emit"](kind, **ev)
both    system_prompt(run) -> str         appended to the system prompt before the first call

Two hooks can change the run. on_llm_request receives the message list and may edit it (Compact does). on_tool_call may raise ToolDenied to stop a tool (Approval does). Everything else observes. A loop running inside a graph inherits the graph's plugins, so one Trace sees the whole run, outer and inner.

Trace: what to log

Trace appends one JSON line per event. It is the most important plugin in the library, because every diagnosis in Chapters 8 and 12 is read from its output.

{"kind": "llm", "run": "cf7618aa", "step": 2, "prompt_tokens": 3970, "completion_tokens": 51,
 "reasoning_tokens": 18, "cost_usd": 0.00013, "ms": 1238, "tool_calls": [{"name": "calc", "arguments": {"expression": "217 * 7"}}]}
{"kind": "tool", "run": "cf7618aa", "step": 2, "name": "calc", "arguments": {"expression": "217 * 7"}, "result": "1519"}
{"kind": "evaluate", "run": "cf7618aa", "step": 3, "passed": true, "feedback": "", "score": 1.0}
{"kind": "node_end", "graph": "article", "node": "write_a", "ms": 49154, "error": null, "keys": ["para_a", "para_a_run"]}

What to log, and why: tokens and cost per call (so you can price and find bloat), milliseconds per call and per node (so you can find the slow stage), every tool call with its arguments and a cut of its result (so you can see what the model reached for and what came back), every verdict with its feedback (so you can find rubric bugs), every route (so you can see why the path went where it went). Text is cut at 2,000 characters per event so a day's trace stays readable. The file is append-only; grep it.

agl viz traces/run.jsonl --open turns a trace into one page: the graph drawn, the waves as chips, every event in order, and a replay button that plays the run back without paying for a model. Use it to show a run to someone who was not there, including yourself tomorrow.

Console, Budget

Console prints one line per step to the terminal for a person watching; off in batch runs, on in development. Budget raises BudgetExceeded when one run spends more than a dollar cap or takes more than a step cap; the loop catches it and ends the run with status "budget". The client's process-wide cap, AGL_BUDGET_USD, is the second net for the whole night. Every unattended loop carries both.

Compact: keeping the history short

@dataclass
class Compact:
    max_chars: int = 60_000
    keep_recent: int = 2
    head: int = 400
    def on_llm_request(self, run, messages):
        total = sum(len(str(m.get("content") or "")) for m in messages)
        if total <= self.max_chars: return
        tool_idx = [i for i, m in enumerate(messages) if m.get("role") == "tool"]
        for i in tool_idx[:-self.keep_recent]:
            c = messages[i]["content"]
            if len(c) > self.head + 80:
                messages[i]["content"] = c[:self.head] + f"\n... [compacted: {len(c) - self.head} characters removed]"

Deterministic and free. Once the history passes a size, every tool result older than the most recent two is cut to its head plus a note of what was removed. The model keeps the gist and the loop stops paying for whole files on every call. Two refinements when the gist is not enough: a model-written summary in place of the cut (one call, when the result was prose), or offloading the full text to a file and leaving a handle the model can re-read with a tool. Both are a few lines in this hook.

Approval: a person in the path

loop = Loop(llm, tools=Toolbox(read_file, write_file, shell),
            plugins=default_plugins() + Plugins(Approval(guarded=("shell", "write_file"), ask=my_policy)))

Guarded tools run only if ask(name, args) says yes. In a terminal that is a prompt; in a server it is an allow-list, a queue a person reviews, or a rule ("writes under drafts/ are fine; anything else asks"). A denial goes back to the model as text and the loop continues. This is the shape of human-in-the-loop that works: the human gates actions, not thoughts, and the agent does not block on a person for anything that does not need one.

Skills: standing instructions

@dataclass
class Skills:
    dir: str | Path = "skills"
    only: list[str] | None = None            # pick a subset per loop
    def system_prompt(self, run):
        files = sorted(Path(self.dir).glob("*.md"))
        if self.only: files = [f for f in files if f.stem in self.only]
        return "# Skills\n\n" + "\n\n".join(f"## {f.stem}\n{f.read_text().strip()}" for f in files) if files else None

Each skills/*.md is one page on how to do one kind of task well, appended to the system prompt under a heading. This is procedural memory: the team's rules, in the repository, versioned, read on every run. agl ships two: plain-writing.md (the voice, and the rule never to invent a number, a study or a citation) and course-chapter.md (the chapter contract). Give each loop only the skills its job needs with only=; a writer does not need the shell safety rules.

When a model keeps breaking a rule, write the rule in a skill before you touch a prompt. A prompt lives in one loop; a skill lives in the project and is read by every loop that opts in.

Presets

def default_plugins(verbose=True) -> Plugins:
    return Plugins(Trace(), Console(verbose=verbose), Budget())

production = default_plugins(verbose=False) + Plugins(Compact(), Approval(ask=policy), Skills(only=[...]))

Plugins() is the minimal preset; default_plugins() is the standard one. A production loop adds Compact, Approval with a policy, and the skills its job needs. The idea that everything around the loop is a plugin is borrowed from the plugin harnesses of 2026, where even the model adapters and the user interface are plugins on a small kernel; four hooks and one emit are enough for a library this size.

Writing a plugin

Priya wants to know how often her writers are sent back by the evaluator.

class RetryCounter:
    def __init__(self): self.fails = {}
    def on_evaluate(self, run, verdict):
        if not verdict.get("passed"):
            self.fails[run.name] = self.fails.get(run.name, 0) + 1
    def on_graph_end(self, graph, state, path):
        print("evaluator rejections per loop:", self.fails)

g.run(state, plugins=default_plugins() + Plugins(RetryCounter()))

She touched neither the loop nor the graph nor the writers. The counter sees every verdict because loops inside the graph inherit its plugins. It tells her two of three chapters were bounced once for length, which tells her the word range in her chapter skill is too tight for first drafts.

Common questions

Why hooks and not inheritance?

Several plugins have to see the same event. A list of objects with optional methods is the simplest thing that allows that, and it keeps the loop ignorant of which plugins exist.

Can a plugin rewrite history?

Only Compact-style edits in on_llm_request, and they should be visible in the text ("[compacted: ...]"). A plugin that silently rewrote messages would make traces lie.

What happens if a plugin raises?

The exception propagates and the loop ends with status "error". Plugins should be boring; Budget and Approval are the only built-ins that raise, on purpose.

Is a skill just a prompt fragment?

Yes, with three properties a pasted prompt lacks: it lives in the repository, it is versioned, and it is read by every run that opts in. The team owns it, not the person typing today.

Why are plugins locked when a graph emits?

Several nodes in one wave run in threads and may emit at the same moment. The engine takes a lock around every emit, so a trace file never interleaves two lines.

Carry this

  • A plugin is an object with some of a dozen hook methods. Two can change the run: on_llm_request edits messages, on_tool_call can deny a tool.
  • Trace everything that costs or decides: tokens, dollars, milliseconds, tool calls, verdicts, routes. Then grep it.
  • Production loops carry Budget, Compact, Approval with a policy, and the skills their job needs.
  • When a model keeps breaking a rule, write the rule in a skill, not a prompt.

Check yourself

1. Which two hooks can change a run, and how?

Answer

on_llm_request may edit the message list (Compact shortens old tool results); on_tool_call may raise ToolDenied (Approval stops a guarded tool and the model reads a denial).

2. What does Compact remove and what does it keep?

Answer

It cuts tool results older than the most recent two to their first 400 characters plus a note of how much was removed, once the history passes a size; recent results and all non-tool messages are untouched.

3. Why does a loop running inside a graph show up in the graph's trace?

Answer

The engine passes its plugins into each node's state, and a loop running as a node merges them with its own, so one Trace receives the loop's events too.
