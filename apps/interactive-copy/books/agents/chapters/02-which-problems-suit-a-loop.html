In this chapter, we will learn the one question that decides whether a task can be given to an autonomous loop at all: can it be measured? We will sort tasks into measurable and non-measurable, split the measurable ones into open-ended and closed, and see why the sentence "what gets measured gets improved" is the engine under everything that follows. By the end you will be able to look at your own work and say which parts a loop could own tonight, and what you must build first for the rest.

The analogy: the sports desk and the opinion page

The sports desk has it easy. There is a score. A story that gets the score wrong is wrong, and a program can check it. The opinion page has no score. Whether a column is good is decided by an editor reading it. Both pages get published every day, but they are run differently. The sports desk can be automated end to end. The opinion page needs a judge before anything else.

Measurable and non-measurable

A task is measurable when a program can print one number after every attempt, and a better attempt moves the number the right way. The whiteboard's second board lists the classic examples of each.

MeasurableThe numberNon-measurableWhy there is no number
Reduce the web page load timemilliseconds to first paintImplement dark modedone or not done, judged by eye
Reduce the app startup timemilliseconds to first screenIntegrate a payment gatewayworks or fails; no run-to-run gradient
Reduce the latencyp50 and p95 in milliseconds (latency is the wait between asking and getting an answer; p50 is the typical wait, p95 the wait the unlucky one in twenty sees)Make onboarding friendliertaste, until you define a proxy
Reduce the processing timeseconds per batchWrite better documentationbetter for whom, by what test
Reduce the memory footprintmegabytes at peakRefactor for clarityclarity has no unit

The left column shares a shape: a program you can run, a number it prints, and a direction that is better. That shape makes an autonomous loop possible. The loop can try a change, run the program, read the number, and decide on its own whether to keep the change. Nobody has to be awake.

The right column is not worse work. It is work that needs a judge. Somebody, or some model with a rubric, has to look at the result and say pass or fail. Until that judge exists, a loop around the task has nothing to loop on. Building the judge is the first job, not the last.

What gets measured gets improved

A loop can only improve what it can see, and a number is the only thing a program can see. The sentence on the third board sounds like a management slogan. Here it is a precise claim about machinery.

by hand    a person profiles, guesses, edits, reloads, squints, repeats      perhaps 5 tries a day
by loop    a program edits, runs the timer, reads the number, keeps or reverts  perhaps 12 tries an hour

The second row is only possible because the timer prints a number. Take the number away and the loop cannot tell a good edit from a bad one. Put it back and the loop runs all night. The projects on the whiteboard's last board, ruff, zstd, mem0, ripgrep, all have a program that prints a number (a speed benchmark, a compression ratio, a memory benchmark score). That is exactly why they appear on a board about loops: each could be the target of a loop tonight.

Open-ended and closed

Among measurable tasks, an open-ended task lets the model decide what to try; a closed task tells it.

measurable
  |-- open-ended    "get the lowest validation loss in 5 minutes; anything in train.py is fair game"
  |                 the model proposes the experiment; the number judges it
  |
  +-- closed        "try these three learning rates and report which is best"
                    we propose the experiments; the number ranks them

karpathy/autoresearch, also on the last board, is the purest open-ended example: one file the agent may edit, one number to lower, a five-minute budget per try, and an instruction to never stop. An exam of fixed tasks with expected answers is closed. Both are loops; they differ in who holds the pen.

Open-ended loops find things you did not think of. Closed loops are cheaper and easier to trust. A grown-up project runs both: a closed exam to catch regressions, an open-ended loop to look for the next improvement, with the closed exam as the gate the open-ended loop has to pass. Chapter 15 builds both for your project.

Making a vague task measurable

You do not need a perfect number. You need a number that moves the right way more often than not. Most non-measurable tasks hide a measurable proxy.

Non-measurable taskA proxy a program can printWhat it misses
Write better documentationa quiz: can a model answer 20 questions from the docs alone?tone, structure
Make onboarding friendlierdrop-off rate at each step, from the logswhy people leave
Write a good chaptera checklist: required sections present, word range, house style; then a rubric judged by a second modelwhether it is actually interesting
Implement dark modea screenshot diff against a reference, pixel distancewhether it looks nice
Answer support tickets wella policy check (no promises, no secrets) plus a sample judged by a rubricwhether the customer felt heard

Two patterns recur in that table and in the whole book. First, a checklist a program can run, which costs nothing and catches structure; it is deterministic, meaning the same input gives the same verdict every time. Second, a rubric judged by a second model, which costs a model call and catches content. The checklist runs first, so the judge only reads what passed. Cheap checks first, expensive judges last.

The left column she can hand to a loop tonight. For the right column she needs, in order: a rubric, a judge model that is not the writer model, and a way to check that the judge agrees with her. She builds those in Part II. The lesson of the board is the order: measure first, then automate.

Try it yourself

The whiteboard sets an exercise and we repeat it: identify five to ten tasks in your own project or domain and categorise them as measurable or non-measurable. For each non-measurable one, write the cheapest proxy you can think of, and what it would miss. Keep the list. In Chapter 15 you will turn the measurable ones into exam tasks.

Common questions

Is a model's score on a rubric a measurement?

It is a measurement of what the judge thinks, which is useful and noisy. Treat it as a number with error bars: judge scores move by a few points between identical runs, so demand a margin before calling a change an improvement.

What if the number can be gamed?

Then it will be. An open-ended loop will find the shortcut if one exists. The fix is in the exam, not the loop: pin the test data, keep the scoring code read-only, never let the loop edit the task it is scored on.

Can a task be measurable but not worth looping on?

Yes. If one try costs an hour of compute, a loop runs twelve tries a day and a person might do better. The method shines when a try is cheap: a minute of training, a second of linting, a cent of model calls.

Why is "what gets measured gets improved" on a board about agents?

Because an agent loop is the first machine that can act on a measurement without a person in between. The slogan used to be about management attention. Now it is about a program's attention, and the program does not get tired.

Open-ended loops sound dangerous. Are they?

They are only as dangerous as what they can touch. autoresearch lets the agent edit one file and forbids installing packages. Scope is the safety mechanism, and it is written down in the brief the loop reads.

Carry this

  • Measurable means a program prints one number after every attempt and better moves it the right way.
  • Non-measurable tasks need a judge before a loop can touch them. Build the judge first.
  • Open-ended: the model picks the experiment. Closed: we do. Run the closed exam as the gate for the open-ended loop.
  • Checklist first, judge last. The pattern repeats through the whole book.
  • Measure first, then automate.

Check yourself

1. Is "reduce the memory footprint" measurable? Why?

Answer

Yes. A program can report peak megabytes after each attempt, and lower is better, so a loop can keep or discard on its own.

2. What is the difference between an open-ended and a closed measurable task?

Answer

In an open-ended task the model decides what to try and the number judges it; in a closed task we specify the experiments and the number ranks them.

3. How do you make "write a good chapter" measurable enough to loop on?

Answer

A deterministic checklist (required sections, word range, house style) that runs first and costs nothing, then a rubric judged by a different model that reads only the chapters the checklist passed.
