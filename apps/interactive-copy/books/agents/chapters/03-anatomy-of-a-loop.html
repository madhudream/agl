In this chapter, we will learn what happens inside a loop, box by box, before we write one. The whiteboard's loop board has seven boxes. We will see that they hide two cycles, not one; name the five ways a loop can end; and step through a recorded run to watch the single most important number in agent engineering, the size of the prompt, grow as tool results come back. By the end you will be able to draw the loop from memory and explain each arrow.

The analogy: the reporter's day

The brief arrives (Prompt). The reporter thinks about what to do (LLM). She makes a call or opens a file (Action) and writes down what she learned (Result). She thinks again with the new notes in front of her. When she has an answer she takes it to the desk (Evaluate). The editor says run it (Pass) or sends it back with a note (Fail). Round again until it runs. Nothing in the loop is cleverer than that.

The seven boxes

Prompt ──► LLM ──► Action ──► Result ──┐
           ▲                           │
           │                           ▼
           └──── Fail ◄── Evaluate ──► Pass ──► Final Answer

The loop has two cycles. The inner cycle is LLM, Action, Result, LLM: the model calls tools until it is ready to answer. The outer cycle is Evaluate, Fail, LLM: an answer that does not pass goes back as feedback. Most frameworks only draw the inner cycle. The whiteboard draws both, and the outer one is what makes a loop trustworthy, because it is the only place where something other than the model decides.

Prompt

Three messages at most: a system prompt (what kind of agent this is, plus standing instructions), an optional context message (a document, a file, a block of remembered facts), and the task.

Word: prompt, system prompt, context

A prompt is everything the model is shown before it answers. The system prompt is the standing part: who the agent is and how it should behave, like the job description pinned above a reporter's desk that she rereads every morning. Context is the material for this one job: the document, the file, the notes. The task is the assignment itself. The model sees all three at once, every time it is called.

Keep the task separate from the context: evaluators and logs want to read the task without forty pages of context around it.

LLM

One call. The whole message history goes in, along with the schemas of the tools the model may call. The reply is either text or one or more tool calls. The model has no memory between calls; each call is a fresh reading of the whole list. This is why the history is both the memory of the run and the prompt of the next step, and why everything a tool returns is paid for again on every later call.

Action and Result

If the model asked for tools, each one runs and its result goes back into the history as a message with the role "tool". Then the loop goes straight back to LLM. The model now sees what happened and decides again. A tool that fails returns its error as text, so the model can read it and correct itself; a tool that raised an exception (Python's way of stopping a program with an error) would end the day instead.

Evaluate

A reply with no tool calls is a candidate answer. It goes to the evaluator: a function that returns pass or fail, with feedback. The evaluator can be a regex (a pattern that matches text, like a search with wildcards: 'only digits', 'ends in .json'), a parser (code that reads a format and complains when it is malformed), a test suite, a build, or a second model reading a rubric (a written marking scheme, the kind a teacher grades essays against). The one thing it must not be is the worker model's own opinion of itself.

Pass, Fail, Final Answer

Pass ends the loop; the answer is final. Fail appends the feedback as a new message and goes back to LLM, so the model sees its own earlier answer and the complaint side by side. After a small number of fails the loop gives up and says so.

Five ways a loop ends

pass        the evaluator accepted an answer                      the good exit
fail        the evaluator rejected one answer too many             the task or the rubric is wrong; read the feedback
max_steps   the model kept calling tools for too many turns        it is flailing; read the trace
budget      a cost or step cap stopped the run                     a safety net, not a plan
error       something raised that was not the model's fault        a bug in a tool or the harness

Every exit returns a result object with the answer so far and the status. A well-built loop never raises to its caller, because the caller is often another loop or a graph that must carry on.

Step through a real run

The simulator below replays one recorded run: three model calls, two tool calls, one evaluation. The tokens, milliseconds and dollars are from the run's trace. Press Step and watch the prompt tokens.

The jump from a few hundred to a few thousand prompt tokens between the first and second call is the number to remember. The file the tool returned is now in the history, and it is sent again on every call until the run ends. Tool results are not free, and the cost arrives later, not when they come back.

Word: token

Models do not read words; they read tokens, pieces of words about four characters long. 'How many lines does the file have' is about eight tokens. Every call is billed by the tokens sent in (prompt tokens) and the tokens the model writes back (completion tokens). Think of column inches in a newspaper: the paper pays for every inch of every edition, and a reporter who attaches the whole archive to every filing is paying for it every day.

call 1   475 prompt tokens      the task and two tool schemas
call 2   3,970 prompt tokens    call 1 + the tool call + 217 numbered lines of a file
call 3   4,022 prompt tokens    call 2 + the arithmetic call + its one-line result
total    8,467 prompt tokens, 593 completion tokens, about ten seconds

Switch the evaluator

In the simulator, change the evaluator from the deterministic check to none, then to a judge. With none, the loop ends at the first answer whatever it is. With a judge, one more model call reads the answer against a rubric and roughly doubles the cost of this small run. That tension, free and strict against expensive and flexible, is the subject of Chapter 6.

What is deliberately not in the loop

No planning step, no memory of its own, no retries of model calls, no streaming. Planning happens inside the model's reply for simple tasks, and as a node in a graph for complex ones. Memory is a plugin that adds to the prompt and listens to the result. Retries live in the client. These are decisions, and the next chapter's code is short enough that you can disagree with any of them.

Try it yourself

Draw the seven boxes for a task you do often. Under Evaluate, write the cheapest check a program could run. Under Fail, write the feedback sentence the model would need. If you cannot write that sentence, you have found the hard part of your agent before writing any code.

Common questions

Why is the whole conversation resent on every call?

Because the model has no memory between calls. Each call is a fresh reading of the whole list. That is also why context engineering matters: everything the model will ever know in this run is in that list.

Where is the planning step?

There is none in the loop. For simple tasks the model plans inside its reply. For tasks with a known structure, planning is a node in a graph.

What stops a model that calls tools forever?

A step cap ends the run with status max_steps, and a budget plugin stops a run that spends too much. Both are safety nets; a run that hits them is a run to read in the trace.

Why append the feedback as a user message instead of changing the system prompt?

Because the model needs to see its earlier answer next to the complaint. The history already holds the answer; one more user turn is the smallest change that gives the model everything it needs.

Can a loop run another loop?

Yes, two ways. A tool can start one (a delegate). Or a loop can be a node in a graph, which is how Part III builds graphs out of loops.

Carry this

  • Two cycles: tools until an answer, feedback until a pass.
  • The history is the memory of the run and the prompt of the next call. Tool results are paid for on every later call.
  • No tool calls means a candidate answer; the evaluator decides if it is final.
  • Five exits, each a status; a loop never raises to its caller.
  • No planner, no memory, no retries inside the loop. Each lives somewhere else, on purpose.

Check yourself

1. What tells the loop that a reply is a candidate answer rather than a request for tools?

Answer

The reply has no tool calls. If it has tool calls, the loop runs them, appends the results and calls the model again.

2. Why did the second call in the recorded run cost 3,970 prompt tokens when the first cost 475?

Answer

The 217 lines the file tool returned were appended to the history, and the whole history is sent on every call.

3. List the five statuses a run can end with.

Answer

pass, fail, max_steps, budget, error.
