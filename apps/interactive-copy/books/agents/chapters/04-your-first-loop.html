In this chapter, we will build the loop from Chapter 3 and read the code that runs it. We will install agl, write a loop with one tool and one check in a dozen lines, run it, read its trace, and then read agl/loop.py top to bottom. By the end you will have a working agent on your machine and know exactly what each line of it does.

The analogy: the first shift

Reading about a newsroom is not working in one. On the first shift you file a short piece, watch the desk route it, read the editor's note, and see your line in the next edition. This chapter is the first shift. Everything after it assumes you have done it once.

The smallest useful loop

from agl import LLM, Loop, Toolbox, check, default_plugins
from agl.std_tools import calc, read_file

llm = LLM()                                      # the worker model

loop = Loop(
    llm,
    tools=Toolbox(calc, read_file),              # what it can do
    evaluate=check(lambda a: a.strip().replace(",", "").isdigit() or "reply with only the number"),
    plugins=default_plugins(),                   # trace to a file, print to the console, cap the budget
)

result = loop.run("How many lines does agl/loop.py have, multiplied by 7? Reply with only the number.")
print(result.answer, result.passed, result.run.usage())

Run it with uv run python examples/loop_hello.py. The console plugin prints each step as it happens:

Read it against the seven boxes. Step 1: the model asks for a tool (Action), the file comes back (Result). Step 2: it asks for the calculator; the exact product comes back. Step 3: it answers with no tool call, so the answer goes to Evaluate; the check says it is a bare number; Pass. Three model calls, two tool calls, one evaluation, a fraction of a cent.

The state of one run

Everything about one execution lives in one object.

@dataclass
class Run:
    name: str
    task: str
    model: str
    id: str                      # 8 hex chars, so traces can be joined
    messages: list[dict]         # the whole conversation: system, user, assistant, tool, ...
    step: int = 0                # how many times the model has been called
    fails: int = 0               # how many times the evaluator said no
    status: str = "running"      # running | pass | fail | budget | max_steps | error
    ms: int = 0
    _usage: list[Usage]          # one entry per model call: tokens, dollars, milliseconds

The messages list is the memory of the run and the prompt of the next call at the same time. There is no separate context object. Whatever is in the list is what the model sees.

The run method, line by line

Here is the loop. Read it once top to bottom, then come back to each box. A few plugin calls are left out; they are the hooks from Chapter 13 and change nothing about the control flow.

def run(self, task, *, context=None, state=None) -> Result:
    run = Run(name=self.name, task=task, model=self.llm.model, state=state or {})
    system = self.system
    if extra := plugins.system_prompt(run):                 # skills, memory: appended to the system prompt
        system = f"{system}\n\n{extra}"
    run.messages = [{"role": "system", "content": system}]
    if context:
        run.messages.append({"role": "user", "content": f"Context:\n{context}"})
    run.messages.append({"role": "user", "content": task})           # ── Prompt

    answer, verdict = "", None
    try:
        while run.step < self.max_steps:
            run.step += 1
            reply = self.llm.chat(run.messages, tools=self.tools.specs or None)    # ── LLM
            run.record(reply)
            run.messages.append(reply.raw_message)

            if reply.tool_calls:                                                  # ── Action → Result
                results = self._run_tools(run, reply.tool_calls, plugins)
                for call, result in zip(reply.tool_calls, results, strict=True):
                    run.messages.append({"role": "tool", "tool_call_id": call["id"], "content": result})
                continue                                                          #    back to LLM

            answer = reply.text                                                   # ── Evaluate
            verdict = self.evaluate(answer, run) if self.evaluate else {"passed": True, "feedback": ""}
            if verdict.get("passed"):
                run.status = "pass"                                               # ── Final Answer
                break
            run.fails += 1                                                        # ── Fail
            if run.fails > self.max_fails:
                run.status = "fail"
                break
            run.messages.append({"role": "user", "content":
                f"Your answer did not pass review. Feedback: {verdict.get('feedback', '')}\nRevise and answer again."})
        else:
            run.status = "max_steps"
    except BudgetExceeded as exc:
        run.status, answer = "budget", answer or f"stopped: {exc}"
    except Exception as exc:
        run.status, answer = "error", answer or f"error: {type(exc).__name__}: {exc}"
    run.ms = int((time.perf_counter() - run.t0) * 1000)
    return Result(answer=answer, run=run, verdict=verdict)

Four things to notice. The continue after tool results is the inner cycle. The while with max_steps is the ceiling on it. The user message built from the feedback is the outer cycle, and max_fails is its ceiling. The try around everything is why the loop never raises to its caller: every exit is a status on a result.

Reading the trace

The console is for watching; the trace is for understanding. The Trace plugin appended one JSON line per event to traces/run.jsonl: a log where every line is one bracketed record a program can read, so a day's work is one file you can search. Two of them:

Word: JSON

JSON is the text format programs use to hand each other structured data: names and values in braces, lists in square brackets. {"step": 2, "cost_usd": 0.00013} is JSON. It is the newsroom's standard form: every desk fills in the same boxes, so any desk can read any other desk's form. Models can write it on request, which is how an answer becomes something a program can act on instead of a paragraph a person has to read.

 "cost_usd": 0.00013, "tool_calls": [{"name": "calc", "arguments": {"expression": "217 * 7"}}]}
{"kind": "tool", "run": "cf7618aa", "step": 2, "name": "calc", "arguments": {"expression": "217 * 7"}, "result": "1519"}

Every problem in Chapter 8 is first seen in a file like this. Get used to opening it, and to grep, the command-line search that finds every line containing a word (grep "error:" traces/run.jsonl shows every tool that failed today). agl viz traces/run.jsonl --open turns it into a page you can replay.

Priya's first loop

Priya writes a loop that drafts one chapter of a course from a brief. No tools: the writer only writes. Her evaluator is a function that checks the draft has the sections her site expects and sits inside a word range, and returns a sentence naming what is missing. On the first run the draft is too long; the loop sends it back with "2,900 words; the range is 1,400 to 2,400" and the second draft fits. She has not written a prompt about length. She has written a check, and the loop did the rest.

Try it yourself

Run the example. Open the trace and find the llm event of step 2; read its prompt_tokens. Change the task so the model has to read a longer file and compare. Set max_steps=2 and watch the status change. Then remove the evaluator and run again: does the answer still come back as a bare number every time?

Common questions

Why uv?

It installs Python and the dependencies in one command and runs scripts in the right environment. pip and a virtualenv work too.

Can I use a model without tool calling?

You can run a loop with no tools and an evaluator, which is a review cycle on text. Tools need a model that returns structured tool calls; nearly all current models do.

What is in default_plugins?

Trace (every event to a JSONL file), Console (one line per step), Budget (stop a run that spends more than a cap). Chapter 13 reads them.

Why does the loop catch all exceptions?

Because the caller is often a graph that must continue, and because a crash in one tool should be a status to read, not a stack trace (the wall of file names and line numbers Python prints when it crashes) that ends the night.

Where does the system prompt text come from?

A short default in agl/loop.py, plus whatever plugins append: skills and memory. Keep it short and put rules in skill files, where they are versioned and reused.

Carry this

  • One client, one loop, tools, an evaluator, plugins: a working agent in a dozen lines.
  • continue after tool results is the inner cycle; the feedback message is the outer one.
  • Every exit is a status on a result. The loop never raises to its caller.
  • The trace is where you will see every problem first. Open it after every run until it is a habit.

Check yourself

1. Which line implements the inner cycle, and which implements the outer one?

Answer

The continue after appending tool results sends the loop back to the model (inner); the user message built from the evaluator's feedback does the same after a fail (outer).

2. What happens when max_fails is exceeded?

Answer

The loop stops with status "fail" and returns the last answer, so a stubborn model cannot run up a bill.

3. Priya never wrote a prompt about chapter length. How did the length get fixed?

Answer

Her evaluator returned a sentence naming the word count and the allowed range; the loop appended it as feedback and the model's second draft fit.
