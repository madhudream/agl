In this chapter, we will learn how a graph runs. Nodes are functions of a shared state, edges say what may run next, and the engine runs every ready node in the same wave, in parallel. We will read the engine, learn the one rule that makes parallel writes safe, meet routers, and see how errors and cycles are kept under control. By the end you will predict the waves of any graph before running it.

The analogy: the morning meeting

The desk does not assign stories one at a time. At the morning meeting the editor looks at what is ready: the three reporters whose briefs are complete go out together. When they are all back, and only then, the rewrite editor can start. Each reporter files into her own slot on the page; two reporters writing into the same slot would be a mess, so the desk forbids it. The morning meeting is a wave. The slots are state keys.

Nodes, edges, state

A node is a function that reads the state and returns the keys it wants to add. An edge says "when this finishes, that may start".

def plan(state: dict) -> dict:
    return {"angles": ["a", "b", "c"], "audience": "students"}

g = Graph("article")
g.node("plan", plan)
g.node("write_a", writer.as_node("Topic: {topic}\nAngle: {angles[0]}", key="para_a"))
g.edge(START, "plan")
g.edge("plan", "write_a", "write_b", "write_c")
g.edge("write_a", "edit"); g.edge("write_b", "edit"); g.edge("write_c", "edit")
state = g.run({"topic": "why agents need evaluators"})

The state is one dictionary. Every node gets a snapshot and returns a dictionary of new keys, which the engine merges in. A node never mutates the state it was given. Three kinds of thing can be a node: a plain function, a loop through as_node (its prompt is a template over the state), or a whole other graph. The engine does not care which.

The engine

The engine keeps three facts per node: which inputs have ever arrived, which have arrived since it last ran, and how many times it has run.

deps[d]   = {s for (s, d) in edges if (s, d) is not a back edge}   # what d waits for
ever[n]   = inputs that have fired at least once
fresh[n]  = inputs that have fired since n last ran
runs[n]   = how many times n has run

def ready(jumps):
    """Router jumps + every node whose inputs have all arrived and something new arrived."""
    wave = []
    for n in jumps + [n for n in nodes if fresh[n] and deps[n] <= ever[n]]:
        if runs[n] >= nodes[n].max_visits:
            errors[n] = f"max_visits={nodes[n].max_visits} reached"
            continue
        wave.append(n)
    return wave
wave = ready([])
while wave:
    for n in wave:
        runs[n] += 1; fresh[n].clear()
    results = run in parallel: nodes[n].fn(snapshot of state) for n in wave      # a thread per node

    jumps, writes = [], {}
    for name, out, error, ms in results:
        for key in out:
            if writes.get(key, name) != name:
                raise StateCollision(f"{name!r} and {writes[key]!r} both wrote {key!r}")
            writes[key] = name
            state[key] = out[key]
        if error:
            errors[name] = error
            if nodes[name].on_error: jumps.append(nodes[name].on_error)
            continue
        if name in routers:
            label = routers[name].route(state)
            jumps.extend(routers[name].targets[label])          # END stops; anything else runs next
        for (s, d) in edges:
            if s == name: ever[d].add(name); fresh[d].add(name)
    save_checkpoint_if_asked()
    wave = ready(jumps)

Read the ready condition slowly. A node runs when all of its inputs have arrived at least once and at least one has arrived since it last ran. The first half is fan-in: the editor waits for all three reporters. The second half makes cycles work: if only one reporter refiles after a review, the editor runs again on the new copy instead of waiting for the other two to refile too.

The one rule: disjoint keys

Two nodes in the same wave may not write the same key. If they do, the engine raises, because that is a bug in the graph, not a race to resolve.

g = Graph("x").node("a", lambda s: {"k": 1}).node("b", lambda s: {"k": 2}).edge(START, "a", "b")
g.run({})      # StateCollision: 'a' and 'b' both wrote 'k'

This is the only place the engine raises. Everything else, a node that throws, a router that returns an unknown label, a cycle that runs too often, lands in state["errors"] and the graph finishes. A collision means two parallel branches were given the same output name, and no run can be trusted until that is fixed, so loud and early is right. The rule is easy to follow: name outputs after the node that makes them, and merge in a node after the fan-in.

Snapshots

Within a wave, nobody sees anybody else. Each node gets a copy of the state taken before the wave starts; writes land after the wave. This is what makes "parallel" safe to reason about: there is no interleaving to think about, only the merge at the end, and the merge is checked.

Routers

A router is a function of the state that returns a label; the label picks what runs next. This is the one place the graph lets the run decide.

g.router("review", lambda s: "pass" if s["ok"] else "fail", {"pass": END, "fail": "edit"})
g.router("classify", lambda s: s["kind"], {"billing": "billing", "bug": "bug", "other": ["reply"]})   # a label may fan out

After the node runs, the engine calls the route function on the state. END stops that path; any other target is jumped to directly: a router target does not wait for its static inputs, because the router is the input. This is how review cycles and classification branches are built. max_visits (3 by default) is what stops a cycle from spinning for ever; when a node hits it, the engine records the fact and the graph drains. max_steps (50 per run) is the outer net.

Errors, retries, resume

A node that raises does not stop the graph. The error is recorded under the node's name, an on_error target gets a turn if there is one, and the rest of the graph continues as far as its inputs allow. Two more controls handle the real world:

retries      Node(retries=2): re-run a node that raised, for transient model or network errors
checkpoint   g.run(state, checkpoint="run.json"): the state is saved after every wave; if the file exists
             when run() starts, finished nodes are not re-run and failed nodes get another turn
state = g.run({"topic": t}, checkpoint="data/course.json")   # crash halfway? run the same line again

Checkpointing is what turns a five-minute graph with a flaky step from a thing you babysit into a thing you run again. Delete the file to start over.

Type a graph, see its waves

Try the sample first: five working nodes, four waves, three nodes in one wave. Delete the fan-out and make it a chain, and the waves become one per node. Add a sixth writer: the number of waves does not change. That is the whole case for graphs when the work is known: more parallel work costs no more wall clock.

sequential     plan, write_a, write_b, write_c, edit, review = 6 steps
in waves       {plan} {write_a, write_b, write_c} {edit} {review} = 4 waves
if a writer takes 45 s       three writers in sequence 135 s; one wave 45 s (the slowest writer)

What the engine records

When a run ends, the state carries _path (the nodes in the order they finished), _ms, and errors. Every wave, node and route is also emitted to the plugins, so a trace shows the graph exactly as it ran, and the console prints it live:

╔═ graph article: 6 nodes
║ ▶ plan
║ ■ plan 11743ms
║ ▶ write_a
║ ▶ write_b
║ ▶ write_c
║ ■ write_a 49154ms  ■ write_b 40259ms  ■ write_c 28705ms
║ ▶ edit
║ ■ edit 30943ms
║ ▶ review
║ ⤷ review --pass--> END
╚═ done: plan → write_a → write_b → write_c → edit → review

The three writers start together and finish in their own time; the editor waits for the slowest.

Common questions

Why threads and not async?

The work inside a node is a blocking model call, threads are enough for six parallel nodes, and the engine stays forty lines shorter. A graph that needed thousands of concurrent nodes would want async.

What if two parallel nodes need to update the same list?

Give them different keys and add a small merge node after the fan-in. The merge is then explicit, testable and cannot race.

Does a router replace the static edges from its node?

No. Static edges still fire. A router adds jumps on top. Most routers sit on nodes whose only ways out are the router's labels, which keeps the picture simple.

What is max_visits for?

The ceiling on how often one node runs in one graph run, 3 by default so review cycles work. When a node hits it, the engine records the error and stops feeding that node, and the graph drains.

What does the checkpoint file contain?

The state without private keys, each node's run count, which inputs have arrived, and the path so far. It is plain JSON; you can read it to see where a run stopped.

Carry this

  • A node is a function of the state that returns new keys. An edge says what may run next.
  • Ready: all inputs have arrived at least once and something new arrived since the node last ran.
  • Ready nodes run in one wave, in parallel, on snapshots. Disjoint keys, or the engine raises.
  • Routers decide a label from the state; targets are jumped to directly. max_visits stops cycles.
  • Node errors are recorded, retries handle flakiness, checkpoints make a run resumable.

Check yourself

1. State the ready rule.

Answer

A node runs in the next wave when every input it depends on has fired at least once, at least one has fired since the node last ran, and it has not reached max_visits.

2. Why does the engine raise on a state collision but not on a node exception?

Answer

A collision is a design bug that invalidates every run, so it must be loud and immediate; a node exception is a run-time failure the graph can record and route around.

3. Three writers take 49, 40 and 29 seconds. How long does their wave take, and a chain?

Answer

The wave takes about 49 seconds (the slowest); a chain would take 49 + 40 + 29 = 118 seconds.
