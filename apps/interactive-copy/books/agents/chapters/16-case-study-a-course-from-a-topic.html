In this chapter, we will build the thing Priya wanted from the start: a graph that takes a topic, or a PDF, and writes a course for her site, well enough that she trusts it before a student sees it. We will design it backwards from the output contract, read every node, run it, and see what the evaluators catch. Then we will show how the same shape writes something else. By the end you will have seen every idea in the book used in one program, and you will know how to adapt it to your own output.

The analogy: a special edition

A special edition is the whole newsroom at once. The editor plans the sections. Reporters write them in parallel, each against the style guide, each checked by a sub-editor before it leaves their desk. A production editor assembles the pages. The printer's proof is the final check: either the edition prints or a page goes back. The course builder is a special edition with a graph for a desk.

Step 1: the output contract

The site that serves the course is a static build: a book is a folder, and build.py --check decides whether it is a book. So the target is a folder with a book.json, a chapters/NN-slug.html per chapter in the site's component vocabulary, and an assets file; and the last node is the site's own checker. Its rules, plus the site's style guide, become a deterministic validator the writers must pass before anything touches disk:

def validate_chapter(html, expect=None) -> bool | str:
    problems = []
    # first line is the meta comment with title, part, minutes, summary; pinned title and part must match exactly
    # no em dash; no exclamation mark; no 
; no widget references; a fragment, not a page
    # every tag balanced; lede, analogy, try, faq, carry, check all present
    # 1,400 to 2,400 words; at least five folded answers
    return True if not problems else "Fix these and resend the whole chapter: " + "; ".join(problems)

Every complaint names the fact and the target, because the writer will read it as feedback. All the complaints come back at once, so a draft is fixed in one retry rather than five.

Three patterns from the catalogue: a sequence, a map, a repair path. The back edge fix -> assemble is a jump, not a dependency, so the first pass runs straight through.

Step 3: the nodes

outline: a planner with a count check

def outline_ok(answer):
    plan = parse_json(answer)
    n = len(plan.get("chapters", []))
    return True if n == chapters else f"the plan has {n} chapters; it must have exactly {chapters}"

outliner = Loop(llm, name="outline", json_mode=True, evaluate=check(outline_ok), max_fails=2,
                system="You design short interactive books for students. Reply with JSON only.")

def outline(s):
    source = f"\n\nSource material (use only this for facts):\n{s['source'][:30000]}" if s.get("source") else ""
    plan = parse_json(outliner.run(f"Topic: {s['topic']}\nDesign a book of exactly {chapters} chapters ..." + source).answer)
    for i, ch in enumerate(plan["chapters"], 1):            # the plan's labels are the law for every writer
        ch["n"] = i
        ch["part"] = ch["part"] if ch.get("part") in plan["parts"] else list(plan["parts"])[0]
    return {"plan": plan, "plan_chapters": plan["chapters"]}

A planner left alone returns one chapter when asked for three, and three different part labels for three chapters. The count is a check with feedback; the labels are normalised in code. Prompts are not where these get fixed.

write: one loop per chapter, two evaluators

def write_one(ch, s):
    pinned = {"title": ch["title"], "part": ch["part"]}
    writer = Loop(llm, name="write", plugins=Plugins(Skills(only=["plain-writing", "course-chapter"])), max_fails=3,
                  evaluate=all_of(check(lambda html: validate_chapter(html, pinned)),             # free, structural
                                  judge(llm, CONTENT_RUBRIC, threshold=0.7, model=JUDGE_MODEL)),   # content, a different model
                  system="You write one chapter of an interactive book as an HTML fragment. Output the HTML only.")
    source = f"\n\nSource material (facts must come from here):\n{s['source'][:20000]}" if s.get("source") else ""
    task = (f"Book: {s['plan']['title']}\nRunning analogy: {s['plan']['analogy']}\nChapter {ch['n']}: {ch['title']}\n"
            f"meta.title must be exactly: {ch['title']}\nmeta.part must be exactly: {ch['part']}\n"
            f"Summary: {ch['summary']}\nMust include: {'; '.join(ch['facts'])}\n"
            f"Length: aim for 1,800 words and stop by 2,200 (hard limit 2,400; first drafts run long).{source}")
    r = writer.run(task, state=s)
    return {**ch, "html": r.answer, "ok": r.passed}

The writers get no tools: they write. They get two skills: the voice and the chapter contract. Their evaluator is all_of: the validator first, free; the content judge second, on the judge model, only for chapters that passed the validator. The source material, when there is one, goes into the task with "facts must come from here", which is grounding. The length line exists because first drafts run long and a retry costs a whole chapter.

Read what the evaluators did. The validator bounced one chapter for length; the writer fixed it in one retry. The content judge bounced a different chapter for being short, carrying the wrong minutes, and leaving out an example the source required; the retry fixed that too. The build check passed on the first try, because nothing reached it that had not already passed the contract. Three chapters in about three minutes, the three writers in one wave, and the result is a book on the shelf of the test copy of the site: cover, sidebar with parts, chapters with lede, analogy, sections, exercises, questions and answers, because the contract demanded each one.

What the evaluators teach you about the graph

length bounces        the skill's range is tight for first drafts: add the target line (done), or widen the range
content bounces       the judge reads the whole source every call and is most of the cost: give it the facts list instead
no build failures     the validator and the checker agree; the repair path is insurance, not a working part
drift without source  without --source the model chooses its own meaning for a term: ground every real build

The second line is the next experiment, and Chapter 15 is how to run it: change the judge's input, run the exam, compare score and cost, keep or discard, log.

Serving it

To build on demand, expose the graph over HTTP. agl serve --graphs examples/course_builder.py accepts POST /graph with the topic and the source text and returns the final state, including book_dir and build_ok. A site hands the user's topic or uploaded PDF to it, reviews the result, and copies the folder in. Chapter 18 covers the review step and the safety around it.

Common questions

Why is the build check a node and not just a test afterwards?

Because a failing build should route to a repair, and a router needs to be in the graph. The real check as the last node also makes the graph's success the site's definition of success.

Why one writer per chapter instead of one writer for the book?

Parallelism and isolation: three chapters take the time of one, and a chapter that fails is retried alone. The cost is coherence between chapters, which the shared outline and analogy mitigate and a continuity editor node would finish.

Could the judge use the worker model to save money?

It would be the worker grading itself. Cut the judge's input instead, which attacks the real cost, the tokens, and keeps the independent reader.

What about a long PDF?

--pdf extracts the text and puts it where --source would. The prompts truncate the source to a fixed size, so a long PDF wants a selection node first: pick the pages relevant to each chapter. That node is a loop with a reader tool.

Is a generated chapter ready to publish?

It is structurally correct, grounded and judged for consistency with its source. It is not yet checked for whether it is interesting. A person reviews it before it is published; that review can itself be a judge node with the site's review protocol as its rubric.

Carry this

  • Design from the output contract backwards; the program that consumes the output is the last node.
  • One loop per item with a validator that returns every complaint at once; a content judge on a different model, only after the validator.
  • The real check as a node, a repair node on fail with a back edge, grounding in the source.
  • The evaluators' bounces tell you where the graph is tight and where the cost is.
  • Change the contract, the validator and the rubric, and the same graph writes something else.

Check yourself

1. Why does every writer validate its chapter before it is written to disk?

Answer

So a structural failure goes back to the model with a precise complaint while the writer still has the context, instead of being found by the build and repaired by a separate node.

2. What did grounding change, and what did the content judge add on top?

Answer

Grounding made the chapters follow the source's meaning of the terms instead of the model's; the judge caught a chapter that was short, had the wrong minutes and omitted a required example, which no structural check could see.

3. To make this graph write a test suite instead of a course, what do you change?

Answer

The contract (the tests run and pass), the validator (one test file per function, imports resolve) and the rubric (tests check behaviour). The shape stays: outline, map, assemble, real check, repair.
